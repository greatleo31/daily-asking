# Daily Asking V1 技术与体验设计

## Context

产品动机和边界见 `proposal.md`。当前应用采用 Flutter、Riverpod 与 GoRouter：`TodayPage` 同时呈现五字段长表单和固定指标，`EntryRepository` 将全部记录作为 JSON 存在 `shared_preferences`，图谱与本地追问尚不存在，`ArtifactsPage` 只保存内存中的模型原始字符串，Worker `/generate` 固定返回 `501`。

现有优势需要保留：`Entry` 字段语义稳定、记录 CRUD/搜索/筛选/导出已可用、API Key 进入安全存储、真实 AI 发送前有披露、提示词输出有结构校验、无依据数字会被阻止、CI 可构建 APK。

本变更采用单机全栈主架构。Flutter 应用和本地数据库构成默认完整产品；BYOK 服务商与 Worker 都是用户主动触发的外部依赖。任何外部能力失败不得破坏本地闭环。

## Goals / Non-Goals

**Goals:**

- 建立稳定依赖方向：界面 -> 应用服务/控制器 -> 领域规则 -> 仓库/客户端 -> 平台与外部服务。
- 让首屏快速记录、本地单题追问和证据图谱共享同一套可测试的证据语义。
- 用版本化关系存储承载记录、问题、答案、产物和来源关系，并安全迁移旧数据。
- 让 AI 工作室先校验、再审阅、后保存，所有产物能追溯来源。
- 将 Worker 收敛为默认关闭、配置固定、受鉴权/限流/超时约束的可选代理。
- 用 G2/G3、少量高价值自动化测试、真实截图和 APK 证据共同完成发布验收。

**Non-Goals:**

- 不建立远程账号、云数据库、跨设备同步或遥测平台。
- 不把 Riverpod、GoRouter 或已有领域对象整体替换为新的应用框架。
- 不为 V1 引入通用图数据库；“证据图谱”是本地数据投影和交互模型。
- 不在客户端实现通用 Agent 对话循环，也不让 Worker 接受任意上游地址。
- 不追求对所有 Android 厂商通知策略的后台保活保证。

## Architecture

### 模块边界

- `lib/app/`：路由、四目的地主壳、主题令牌和全局恢复状态。
- `lib/features/journal/`：记录编辑、搜索、筛选、导出和兼容领域模型。
- `lib/features/evidence/`：快速记录用例、本地追问规则、问题/答案状态、图谱投影和证据详情。
- `lib/features/artifacts/`：来源选择、生成协调、结构化草稿、编辑保存、产物列表和来源回跳。
- `lib/features/settings/`：BYOK/网关模式、提醒偏好、主题和隐私设置；不直接暴露密钥值。
- `lib/core/database/`：数据库打开、表定义、迁移、事务和仓库实现。
- `lib/core/llm/`：直连与网关客户端、超时、响应解析和稳定错误。
- `gateway/`：可选 Worker 的鉴权、校验、限流、上游转发和脱敏响应。
- `.github/` 与 `docs/`：验证、签名、截图、发布和开源治理。

### 依赖规则

领域对象和规则不得依赖 Flutter 控件、SQLite API 或 HTTP。页面只调用应用层用例，不直接读写数据库、安全存储或 API Key。仓库接口位于功能/领域边界，具体 Drift 实现位于 `core/database`；AI 客户端只接收当前用例已经最小化的请求对象。

`JournalController` 在数据迁移期间作为兼容入口逐步改为仓库驱动，不同时维护两套互相竞争的页面状态。证据图谱读取仓库提供的只读投影，不能反向修改原始记录。

## Decisions

### 1. 使用一项产品史诗和连续大功能分支

`product-foundation-v1` 在 G3 和全部任务完成前保持活动。规划分支合入后，按以下顺序从最新 `main` 创建并推送独立分支：

1. `feature/visual-foundation-v1`
2. `feature/local-evidence-store`
3. `feature/daily-evidence-loop`
4. `feature/ai-evidence-studio`
5. `feature/optional-ai-gateway`
6. `feature/release-v1`

每个分支只完成对应任务并更新同一 `tasks.md`/`execution.yaml` 证据。这样避免多个重复 PRD，同时让回归范围、提交和 PR 可独立审查。

备选方案：每个分支创建完全独立的 OpenSpec 变更。它更易单独归档，但会复制产品范围、产生规格漂移，并增加 Agent 上下文。V1 采用单史诗，后续互不相关功能恢复一功能一变更。

### 2. 四目的地信息架构，证据页吸收记录池

底部导航固定为“今日、证据、工作室、设置”。“今日”只负责快速捕获与当前一问；“证据”组合图谱、筛选和记录管理；“工作室”组合来源选择、生成、审阅和已保存产物；“设置”承载 AI、提醒与隐私。

GoRouter 使用有状态壳或等价导航状态保存各目的地的滚动、筛选和草稿。编辑/详情使用页内路由或底部面板，返回后恢复来源上下文。

备选方案：保留“记录池/产物”技术命名。改动更少，但无法表达“先积累证据、再形成产物”的用户心智。

### 3. 快速记录与详细编辑分离

首屏只要求一句 `task`，保存动作先提交记录，再计算是否需要一个本地问题。已有五字段继续存在于详细编辑和 AI 来源中，不破坏导出兼容。快速路径不在一个页面展开五个文本框。

本地问题引擎输入为记录字段和既有问答摘要，输出为零或一个 `EvidenceQuestionDraft`：类型、文案、原因和优先级。V1 使用固定、可版本化规则，建议优先级为结果/验证、范围、行动与个人贡献、协作、难点/取舍。规则不调用模型，且对同一输入保持确定性。

答案作为独立实体保存，不强行拼接回用户原文；AI 来源组装器可以同时读取记录字段和已回答问答。选择“稍后”保留待回答状态，选择“跳过”记录该问题版本已跳过，避免立即重复骚扰。

备选方案：保存前强制填完 STAR 字段。它能提高单条完整度，但直接违背 30 秒闭环，继续造成低频使用。

### 4. 证据图谱采用派生投影而非图数据库

`EvidenceMapProjector` 从记录、问答、日期和标准化标签计算只读模型：

- 日期强度：该日有效证据数量，不等同于工作绩效。
- 完整度：当前记录覆盖的证据维度比例，显示缺口而非评分人格。
- 主题：用户标签和可解释的本地归一化结果，不由 AI 猜测公司/项目。
- 连续性：可展示记录节奏，但空白日不改变历史节点和完整度。

数据规模在 V1 预期较小，先在查询层聚合；只有真实性能证据显示需要时才增加可重建缓存表。点击单元必须能回到来源记录。

备选方案：Canvas 自绘网络图。视觉新颖但可访问性、点击命中、文本适配和测试成本高。G2 原型优先采用稳定网格/时间带与主题聚合，必要的连接关系用受约束绘制层表达。

### 5. 晨昏视觉使用信息令牌，不延续紫色宇宙模板

视觉分支先产出真实 Flutter 原型和多状态截图，再经 G2 进入全面实现。设计系统约束：

- 使用矿物白/墨绿/朱红/琥珀/湖蓝等多角色颜色，深色主题使用中性近黑与低饱和表面；不让紫蓝或米色成为单一主色。
- 页面背景使用稳定实色或与数据有关的区域变化，不使用装饰光球、玻璃叠卡或营销式大标题。
- 卡片仅用于重复记录项、模态框和真正有边界的工具，圆角不超过 8px；页面分区保持无框。
- 图标优先使用 Material/Lucide 等现有图标库；常见操作使用图标与 tooltip，不手绘重复 SVG。
- 字体不随视口宽度缩放，字间距为 0；固定网格、导航和工具栏使用稳定尺寸约束。
- 状态切换动效控制在约 160-240ms；禁止无限呼吸、视差和无意义循环。系统减弱动态效果时使用静态替代。

验收视口至少覆盖约 360x800 和 412x915，并检查亮/暗主题、最长中文文案、键盘打开、加载/空/错/成功和减弱动态效果。

### 6. 使用 Drift / SQLite 和失败安全迁移

数据分支引入 Drift 与 SQLite Flutter 绑定，最终版本必须在实现时根据 Flutter 3.44 / Dart 3.12 和 Android 构建环境查询官方包信息后固定。计划表：

- `entries`：保留现有 id、date、task、context、action、result、blocker、createdAt、updatedAt，并以规范化关系保存 tags。
- `evidence_questions`：id、entryId、ruleVersion、kind、prompt、reason、status、createdAt、updatedAt。
- `evidence_answers`：id、questionId、content、createdAt、updatedAt。
- `artifacts`：id、type、content、promptVersion、modelInfo、route、createdAt、updatedAt。
- `artifact_sources`：artifactId、当前 entry 关联和最小来源 tombstone，用于来源删除后明确显示缺失，不保留已删除正文。
- `schema_meta`：结构版本、旧数据迁移状态和脱敏失败信息。

API Key 继续只进入 `flutter_secure_storage`；提醒偏好等非敏感小设置可继续使用 `shared_preferences`，不得混入证据实体。

旧数据迁移流程：读取但不改写 `daily_asking.entries.v1` -> 全量解析/校验 -> 单事务按稳定 id 插入 -> 核对数量与字段 -> 提交迁移标记。任一步失败则事务回滚，旧载荷不变。成功后至少保留旧载荷到 V1 稳定期结束，避免 Beta 回滚没有恢复入口；新版本只以数据库为权威，防止双写漂移。

备选方案：继续整包 JSON。依赖少，但任一写入会重写全部记录，无法可靠承载关系、事务与迁移状态。

### 7. AI 工作室采用结构化草稿生命周期

生成流程分为：选择来源 -> 构建最小上下文 -> 出站确认 -> 调用 -> 解析/契约校验 -> 事实风险校验 -> 结构化草稿 -> 用户编辑 -> 显式保存。

`ArtifactDraft` 在内存中保存解析后的内容、缺口、追问和风险；校验失败只产生错误状态。保存时通过仓库事务写入 `artifacts` 与 `artifact_sources`。不保存原始 API Key、完整请求、系统提示词或服务商原始错误正文。

删除来源记录时硬删除用户正文，同时保留不含正文的来源 tombstone，使历史产物能说明“来源已删除”。已保存产物不因来源更新而自动改写。

备选方案：保存模型原始字符串。它不能可靠区分内容与风险，也不能支撑来源回跳和后续编辑。

### 8. 直连与可选网关共用窄客户端契约

应用层只依赖 `LlmClient` 和稳定错误类别。直连客户端继续调用用户配置的兼容端点；网关模式调用固定网关基址并用安全存储中的访问令牌鉴权。两种模式都应用请求超时、响应大小边界和出站披露。

Worker 只开放 `GET /health` 与 `POST /v1/chat/completions`（可保留 `/generate` 的明确迁移响应）。部署配置：固定上游基址、允许模型、上游 API Key secret、网关访问令牌哈希 secret、请求大小/超时和 Rate Limiting binding。客户端不能覆盖上游地址或密钥。

Worker 在转发前校验 Bearer token、JSON、消息角色、字段白名单、模型和体积；使用 `AbortController` 超时，不自动重试可能产生费用的生成。日志只包含 requestId、路由、状态、延迟和错误类别。缺少鉴权、上游或限流配置时 `/health` 报告未就绪，生成返回稳定错误。

备选方案：把用户 BYOK Key 转交 Worker。它增加密钥暴露面且没有必要；V1 网关使用部署方密钥与独立访问令牌，BYOK 仍直接发送给用户服务商。

### 9. 发布分为 Beta 验收与正式签名

普通 PR CI 继续运行依赖安装、分析、现有测试和临时候选 APK 构建。`feature/release-v1` 增加独立发布工作流：从 GitHub Environment/Secrets 恢复仓库外 keystore 与属性，构建签名 APK，计算 SHA-256，上传候选资产；日志不得打印 secret。

`v0.2.0-beta` 用于 G3 设备验收，可使用清楚标记的候选签名。完成连续 5 个工作日自用验收、迁移检查、关键截图、AI 事实边界和安装升级检查后，才创建正式签名 `v1.0.0`。MIT、中文 README、架构/隐私/贡献/安全文档和真实截图在 Beta 前齐全。

备选方案：直接把调试签名 APK 标为 V1。它无法提供稳定升级身份，也与生产级声明不一致。

## Frontend State Flow

### 今日

`loading -> ready(draft) -> saving -> question|feedback -> ready`。保存失败回到含原草稿的 `saveError`；问题答案失败保留答案草稿。页面不得通过全局 Snackbar 作为唯一状态证据，关键失败靠近操作呈现。

### 证据

仓库流同时驱动图谱投影和记录列表。筛选条件是页面状态，不修改数据。投影失败只影响图谱区域，记录列表仍可恢复访问。

### 工作室

`selecting -> disclosure -> generating -> reviewableDraft -> saving -> saved`。取消披露回到选择；网络/鉴权/限流/超时/契约错误进入不同可操作状态；已有产物不因新请求失败而消失。

## API Contract

网关请求只接受兼容聊天补全的必要字段：`model`、`messages`、受限 `temperature` 和 `max_tokens`。拒绝工具执行、任意 URL、文件、流式上传和未知顶层字段。请求最大体积、允许模型和超时由部署配置约束。

错误响应统一包含：

```json
{
  "error": {
    "code": "rate_limited",
    "message": "请求过于频繁，请稍后重试"
  },
  "request_id": "..."
}
```

客户端按稳定 `code` 映射用户提示，不展示上游原始正文。成功响应只保留客户端所需 choices/model/usage 字段和 request id，响应头包含 `Cache-Control: no-store`。

## Security, Logging, Errors, Observability

- API Key、网关 token、签名凭据只通过系统安全存储或部署 secret 流动。
- 应用日志使用既有 `SafeLogger` 边界扩展，只记录操作类别、状态和脱敏异常；不记录证据正文、提示词和响应。
- 数据库不存任何凭据或安全存储别名；JSON/Markdown 导出和迁移包继续执行敏感字段排除。
- 本地问题引擎和图谱均不联网；本地提醒不上传日程或行为。
- 应用不做远程遥测。Beta 证据来自本地可见统计、人工验收表、CI 日志、APK 哈希和真实截图。
- Worker 按访问主体限流，生成不自动重试。只有健康检查可用于部署观测，不记录用户内容。
- 所有用户错误都提供下一步：保留草稿、重试、检查凭据、调整来源或打开恢复说明。

## Testing and Acceptance

遵循用户确认的“少量测试、以验收为主”：每个大功能新增 1 至 2 组覆盖最高风险的自动化测试，不追求页面细节穷举。已有 10 个测试必须继续通过。

- 视觉：组件烟雾测试可选；强制多视口真实截图、亮暗/键盘/最长文本/状态验收。
- 数据：强制迁移幂等与失败回滚两组关键测试。
- 每日闭环：强制问题规则确定性与保存失败保留草稿关键测试/验收。
- AI：强制非法结构/无依据内容不可保存，以及来源关系保存关键测试。
- 网关：强制未授权不外呼，以及成功/上游错误映射关键测试。
- 发布：以 `flutter analyze`、完整既有测试、签名 APK 构建、安装升级和 G3 清单为主。

自动化通过只能成为门禁证据，不能写入 G2/G3 人工批准。

## Migration Plan

1. 合入产品基础规划，保持 G1 待项目负责人确认。
2. 在视觉分支产出关键状态原型和截图；获得 G2 后完成壳、主题和页面结构。
3. 引入数据库与仓库适配，完成旧数据只读解析、事务迁移和回滚测试；先不删除旧载荷。
4. 接入快速记录、本地一问、图谱投影和可选本地提醒。
5. 接入结构化 AI 草稿、来源关系、编辑保存和直连/网关模式状态。
6. 修复 Worker 并完成独立安全验证；客户端默认仍为直连。
7. 完成开源与签名发布准备，构建 `v0.2.0-beta` 候选并执行 G3。
8. 修复 Beta 验收问题后，以仓库外签名发布 `v1.0.0`，同步长期规格并归档本变更。

## Rollback Strategy

- 每个大功能独立合并；回归可通过普通反向提交回滚对应功能，不重写 Git 历史。
- 数据库迁移失败时事务回滚并继续保留旧 JSON；迁移成功后旧载荷至少保留到 V1 稳定期结束。
- UI/闭环回滚不得回退数据库结构；旧页面通过仓库兼容接口读取新库，避免让已迁移用户降级到整包 JSON 写入。
- 网关可通过客户端配置立即关闭；Worker 部署回滚不影响 BYOK 直连和本地功能。
- Beta 未通过 G3 时不创建正式标签；已经上传的候选必须明确标记撤回或预发布，不覆盖同名正式资产。

## Risks / Trade-offs

- [单史诗持续时间长，任务状态可能漂移] -> 每个分支只更新自身 task 与紧凑验证证据，合并前运行 OpenSpec 严格校验。
- [视觉先于数据会产生接口返工] -> 视觉分支只依赖仓库/投影接口和真实现有记录，不预埋数据库细节。
- [30 秒目标受输入速度影响] -> 验收使用固定短句脚本并统计界面步骤，同时保留详细编辑入口，不把目标伪装成线上数据。
- [关系迁移扩大代码量] -> 首先迁移核心 Entry 和必要关系，不引入通用同步、历史版本或全文检索框架。
- [保留旧载荷占用空间] -> 仅保留一个受控兼容期，并在正式清理前提供导出和明确迁移证据。
